# Tincall 连接端部署指引

独立模式使用配置好的模型、语音识别与合成服务即可通话，本地记录不需要部署云端。本指引用于连接端的 Supabase 或 Node 部署，以及可选的通话备份、MCP、后端转发与主动来电。保存连接不等于启用了备份、模型生成或来电推送，需按所选功能继续配置并验证。

## 推荐入口：App 内部署

打开设置 → Tincall 云端 → 部署或更新服务：

1. 打开 Supabase 控制台，登录并选择自己的组织；没有组织时先创建个人组织。可从 Free 套餐开始，额度、费用与闲置暂停规则以控制台为准。
2. 点击 **New project**。项目名称可填 Tincall，生成并妥善保存数据库密码，选择离使用者或所用服务较近的区域，其他选项保留默认。数据库密码不需填入 App。等项目就绪后，在 Supabase 控制台打开该项目，点击项目网址右侧的 **Copy**，在菜单中选择第一项 **Project URL**（形如 `https://项目编号.supabase.co`），直接粘贴到 App；也可以直接复制浏览器地址，或只复制其中的项目编号。不要复制下面的 API key。
3. 在账号设置 → **Access Tokens** 创建本次部署用的 scoped Personal Access Token，可命名为 Tincall deployment。创建时先选择项目所在的组织，再把项目范围限定为这一个项目；许可只有「无法访问／只读／完全访问」时，选「完全访问」。这里的完全访问只作用于前面选定的项目；部署成功后可以提前删除或撤销。不要使用未限定项目的组织级令牌，也不要使用项目的 anon、publishable 或 service_role API Key 代替。
4. 返回 App，填写访问令牌和项目编号。部署会自动在这个项目里建立内部数据归属，不需要另外注册账号或填写邮箱。
5. 点击「开始部署或更新」。首次部署通过 Supabase Management API 检查项目及旧安装，生成手机／worker 令牌，执行现有数据库迁移，建立私有存储、部署服务函数、填写 Vault／定时任务，绑定数据归属，最后检查服务并保存日常连接。
6. 看到「部署完成，已保存连接」后，点击「选择接下来要使用的功能」。在设置 → **Tincall 云端 → 云端同步** 中选定服务、检查连接并开启「自动同步通话内容」，即可双向同步文字、图片与摘要；录音需另外开启「同步已保存的录音」。MCP 平台配置在对应联系人的编辑页设置；后台来电在 **设置 → Tincall 云端 → 后台与定时来电** 设置，不会因部署完成而自动启用。

部署管理访问令牌不持久保存，成功后可在 Supabase 撤销。日常手机令牌及本机部署记录保存在 Keychain，不记录到普通请求日志。发生失败时，已完成的资源保留；核对步骤提示后，在原 iPhone 上继续重试。项目已有其他安装但本机没有对应部署记录时会停止，避免覆盖原令牌或数据；已有部署应选择「连接已有服务」。

部署不会代替 Supabase 账号／组织／套餐的创建与费用确认，也不会自动设置外部平台的生成接口或开启后台来电。商店版构建 11 起，App 内部署或更新在项目尚未配置发送端时会自动接入官方来电推送；自签版与命令行部署仍需按推送指南配置自己的发送端。部署后可按需开启云同步、配置联系人接入或后台来电。

### 更新已有服务

App 更新不会自动更新已部署的服务，只有更新涉及连接端功能或协议时才需升级服务。首次部署按下文操作；已有安装按本节原路径升级，勿重新初始化。

由这台 iPhone 部署的 Supabase 项目，可在「部署或更新服务」填入原项目地址和有效的部署管理令牌，补齐迁移并重新部署服务程序；保留数据、手机／worker 令牌、已有服务配置及 Vault。每次部署或更新都需填写有效令牌；旧令牌过期或已撤销时，在 Supabase 令牌页面重新创建，复制后填入 App 的「部署令牌」。此路径不是编辑已有服务配置的入口。

通过电脑或服务器部署的服务，请前往 GitHub 上的 Tincall 代码仓库获取新版源码，并按原部署方式更新：Supabase 部署应用新增迁移并重新部署函数，沿用原私密配置；Node／Docker 部署重复执行原安装命令。不要重新生成手机／worker 令牌或重建数据库，也不要用手机首次部署覆盖电脑或服务器部署的服务。

更新后，在「Tincall 云端」刷新服务版本。服务通过 `/capabilities` 的 `server_version` 报告部署版本，与协议字段 `version` 分开；低于 App 所需版本或没有该字段时会提示更新。检查失败时先核对连接、令牌与服务状态，不能据此判断已经过旧。服务升级后，还需在外部 AI 平台刷新 MCP 工具列表或重新连接。

## 四种通话接法与唤醒桥

仓库提供可运行的通用接入程序 [`connector/wake-adapter.mjs`](../connector/wake-adapter.mjs)。它保持唤醒订阅，收到事件后自动读齐消息，再通过你配置的命令启动一次外部 AI 任务；AI 用专用 MCP 回复并结束，本轮不会挂起等待。

**需要自行配置外部 AI 的启动命令和专用 MCP。** 按 [唤醒桥接入指南](../connector/README.md#唤醒桥接入) 保存 App 复制的 JSON，然后在能启动该 AI 的电脑或服务器运行接入程序。若外部平台支持自动化，也可在该平台自行配置相同的接收事件与启动任务流程。一键部署准备 Tincall 服务端接口；外部 AI 的启动方式由所用平台决定，不能只添加 MCP 地址便完成唤醒。平台没有任务启动入口时，需要先配置其支持的自动化方式。

默认在通话建立（`reason: answered`）和每轮新输入（`reason: input`）时发送事件。接入方可在自己的流程中选择处理哪些事件；例如只处理 `input`，便是等待手机一方先说话再启动 AI。事件只携带标识，消息从 `input.url` 读取，调整筛选不需要修改 Tincall 服务。

| 接法 | AI 与上下文在哪里管理 | 如何开始下一轮 |
| --- | --- | --- |
| 独立模式 | 手机直连模型 API，由 Tincall 管理 | 手机发起模型请求 |
| 普通 MCP | 外部 AI 平台 | AI 回复后按联系人的 MCP 等待设置收取下一句，超时可继续等待；手机拨出不会自动启动 AI |
| MCP＋唤醒桥 | 外部 AI 平台 | 接通和每轮输入触发事件，平台启动一次 AI 任务，回复后立即返回 |
| 后端直连 | 已适配 Tincall 通话接口的后端 | 后端接收每轮输入并生成，无需 MCP |

联系人页保留独立模式、MCP、后端三个选项；在 MCP 内切换普通 MCP／MCP＋唤醒桥。两种接入方式共用传输方式、URL 和 Authorization 的页面布局；桥接方式另提供当前联系人的唤醒接口配置复制按钮，配置内包含唤醒和输入地址。说明统一放在上方信息区。新联系人可在同页保存并复制，不需要退出再打开。所选方式会随联系人保存，选择本身不替外部平台建立唤醒订阅。后端也可通过部署的连接服务转发到真实生成／取消接口，这与唤醒桥分开。

唤醒桥需要当前连接端程序与数据库迁移；首次部署自动包含，已有安装按「更新已有服务」升级。部署完成页可点 **获取唤醒桥配置**；以后在 **Tincall 云端 → 已保存的服务 → 获取唤醒桥配置** 再次获取。先保存一位选择此服务的 MCP 联系人，再选择该联系人复制接入 JSON。每位联系人拥有独立桥接凭据，重复获取不会变更；重置后需重新交给平台。新版配置为 version 2，另含立即读取的 input 地址和专用 MCP 地址；已有接入须更新服务并重新复制配置，无需重置凭据。

平台接入端在模型任务之外维持带鉴权的 SSE 唤醒订阅，先取齐新增发言及实际图片，再续接该联系人的同一会话。游标、消息 ID 和事件 ID 只由接入程序内部使用；交给 AI 的 content 包含 XML 发言与紧随对应消息的原生图片块。名字为空时省略 name，开启时间感知时附带手机本地 timestamp，正文保留在 `<text>` 内；图片不放进 XML。朗读要求仅在通话开始时提供一次，后续任务沿用会话上下文。AI 通过专用 MCP 的 `tincall_reply` 提交完整 `text` 后结束任务，新输入随后唤醒；后续输入不会取消正在写的这条回复。主动拨号仍会挂起等接听，接通结果交给拨号的任务继续说话。HTTP 使用 `/mcp/wake`，旧式 SSE 使用 `/mcp/sse`，均使用桥接专用凭据。空闲时不轮询，断线重连恢复待处理输入，重复唤醒合并。完整接入步骤见 [连接端说明](../connector/README.md#唤醒桥接入)。

## ChatGPT / Claude MCP 授权与残留通话

使用新版 App 的「部署或更新服务」补齐 OAuth 授权及通话占用回收迁移，并更新服务程序。ChatGPT 添加自定义 MCP 时填联系人页复制的 HTTP URL（末尾 `/mcp`），身份验证选 **OAuth**，高级设置使用动态客户端注册，不需手填客户端密钥。Claude 自定义连接器使用相同的 HTTP URL，身份验证选择 **Sign in now**，OAuth client 选择 **Register automatically**。

授权页显示一次性授权码。在 Tincall 设置中打开对应的已保存云端连接 → **MCP OAuth 授权**，输入授权码，选择允许访问的 MCP 联系人并确认。ChatGPT 和 Claude 都使用这个授权入口。查看服务及授权无需关闭后台来电；已绑定时只锁定连接配置的修改。回到发起连接的原浏览器授权页面刷新，继续完成连接。授权只开放这位联系人的 MCP 通话操作，不开放其他联系人、备份或手机管理权限；授权码十分钟有效。Supabase 默认域名不能直接呈现函数返回的 HTML，因此授权确认放在 App 内，不需要额外网站。此流程不是 Supabase 管理授权，不使用部署 PAT。

同一云端账号只允许一通未结束通话，联系人专用凭据看不到其他联系人的通话。遇到 `call_busy` 但当前联系人返回 `call:null`，可在同一云端连接的 **检查云端通话状态** 页面检查；确认旧通话不再使用后可手动结束。这里只在进入页面或手动刷新时查询，服务端存在记录不等于手机仍在通话。新版服务复用实际通话的事件请求记录手机在线状态；手机断开超过三分钟后，worker 或下一次拨号会回收旧通话。正常连接中即使保持沉默也不回收，MCP 查询不能替离线手机续期，不新增空闲轮询。

联系人切换到独立或后端模式并保存后，原 MCP 凭据保留，但不能再向该联系人发起 MCP 来电；工具会明确返回 `contact_mode_mismatch` 和当前模式。切回 MCP 并保存后可继续使用原凭据。新版「部署或更新服务」包含联系人模式迁移，并同步本机已有 MCP 联系人模式，无需重新注册联系人。

## 电脑安装（备选）

电脑安装脚本仍可使用：先在 Supabase 创建项目与归属自己的 Authentication 用户，准备 Project Ref 与用户 UUID；电脑安装并登录官方 Supabase CLI，然后在 Tincall 源码根目录执行：

```sh
sh connector/setup-cloud.sh PROJECT_REF AUTH_USER_UUID
```

首次安装会先检查旧配置，避免覆盖已有令牌；失败重试复用原配置。脚本生成随机手机／worker 令牌，调用现有部署脚本，私密文件默认保存在 `~/.config/tincall/cloud/PROJECT_REF/`。也可用第三个参数指定仓库外的绝对目录。令牌不输出到终端。

生成的 `tincall-cloud.json` 只包含日常连接信息。通过电脑或服务器部署后，可在「连接已有服务」页面填写部署结果中的服务地址与手机访问令牌。通过 App 一键部署后会自动保存连接，无需再次填写。私密文件不得提交源码或分享给他人。电脑安装和手机自动部署的旧安装保护各自生效，不要用另一条路径覆盖现有项目。

## 在自己的电脑或服务器安装（不使用 Supabase）

项目也提供现成的本地安装脚本，使用 SQLite 存储，不需要 Supabase 账号。先安装 [Node.js LTS](https://nodejs.org/)（至少 22.5，支持内置 SQLite），取得项目源码后，在仓库根目录运行：

```sh
# macOS / Linux
sh connector/install-local.sh
```

```powershell
# Windows PowerShell，无需 WSL
powershell -NoProfile -ExecutionPolicy Bypass -File connector\install-local.ps1
```

脚本生成并复用私密令牌、准备数据目录、启动后台服务和配置受当前系统支持的自启；不会替用户安装 Node 或 Docker。已有 Docker 时也可选择 Docker 方式。默认地址只供电脑本机访问，手机必须使用可达的 HTTPS 地址：可配置自己的反向代理，或安装 cloudflared 后增加 `--tunnel`（Windows 为 `-Tunnel`）。将得到的 HTTPS 基础地址和手机令牌填入 App「连接已有服务」。电脑须持续开机且不能休眠；快速隧道重启后地址可能变化。

本地安装、HTTPS 接入、更新与停止的完整步骤见 [连接端安装说明](../connector/README.md#部署到自己的电脑或服务器)。它不会自动完成 AI 平台生成接口或 Apple 推送配置。

以下为 Supabase 项目的手动配置与更新方式。

## 1. 准备自己的项目

在 Supabase 创建或选择项目，并在 Authentication 中建立一个归属自己的用户，记下该用户 UUID。安装并登录官方 Supabase CLI，在 Tincall 源码根目录执行后续命令。

把 `connector/env.example` 复制到仓库外的私密文件，例如 `~/tincall-private/secrets.env`，限制为自己可读写。不要提交该文件。手机令牌使用密码管理器生成的随机值，和 worker 令牌分别设置。

`TINCALL_CLIENTS` 用一整行 JSON 配置手机令牌和用户归属：

```text
TINCALL_CLIENTS=[{"token":"REPLACE_WITH_PRIVATE_RANDOM_PHONE_TOKEN","owner_id":"AUTH_USER_UUID"}]
TINCALL_WORKER_TOKEN=REPLACE_WITH_DIFFERENT_RANDOM_WORKER_TOKEN
TINCALL_BINDINGS=[]
TINCALL_ALLOWED_ORIGINS=[]
```

仅做备份时不需要联系人绑定、平台凭据或 APNs 凭据。不要给手机令牌加 `contact_id`：带此字段的是单联系人令牌，不能读取个人备份。也不要把 Supabase service-role、CLI 管理令牌或 worker 令牌填入手机。

## 2. 部署数据服务

```sh
sh connector/deploy.sh PROJECT_REF /绝对路径/secrets.env
```

替换项目标识和文件路径。脚本会链接项目、应用 migrations、设置服务端 secrets，并部署 `tincall` Edge Function。Supabase 托管环境自动提供保留的 `SUPABASE_*` 变量；部署脚本不会将示例文件里的这些占位值或 APNs 私钥上传到函数。

数据库迁移创建用户隔离规则、私有 `tincall-private` 存储桶和服务数据结构。部署命令成功不代表已完成一次备份；还需按下一步在 App 检查并同步。

图片消息所需的[数据库迁移](../supabase/migrations/202610210003_tincall_message_images.sql) 随 App 部署与 CLI 部署自动执行，无需另行执行 SQL。手动安装过旧图片 SQL 的服务也可沿用原配置升级。录音与图片共用的私有存储桶和权限随基础迁移创建；是否保存录音、允许录音备份仍须在 App 中分别开启。

「记录管理 → 清空当前云端备份」会先读取当前服务的备份并显示确认数量，仅删除确认的备份文字、图片、摘要及已备份录音。本机记录、MCP 通话数据及其图片、来电计划保留；删除墓碑阻止自动或手动同步重新上传这些记录，新通话仍可同步。需要支持 `backup_only_deletion` 的新版服务，旧服务会先提示更新，不执行删除。网络中断时沿用原请求续跑；版本冲突时刷新后重新确认剩余备份。此按钮不清空整个数据库。

## 3. 在 App 填写连接

1. 打开设置 → Tincall 云端 → 连接已有服务。
2. 服务地址填写 `https://PROJECT_REF.supabase.co/functions/v1/tincall`，不是项目根 URL，也不加 `/mcp`。
3. 访问令牌填写 `TINCALL_CLIENTS` 中绑定到自己 Auth 用户的手机 token。
4. 点击「检查连接」，通过后保存服务。再到设置 → Tincall 云端 → 云端同步，选择同步目标并检查。
5. 开启「自动同步通话内容」。如需立即执行，可点「立即同步」；不开自动同步也可使用此按钮。录音需另外开启「同步已保存的录音」，授权按具体服务与所属账户分别保存。

自动同步默认关闭；此前允许过手动同步也不会自动开启。开启后，App 打开、回到前台、本机通话或摘要保存，以及同步设置或目标改变时安排同步；通话期间暂缓。同一批同步上传本机新增或更新的文字、消息图片和摘要，并下载云端新增或更新的记录。联系人与设置只留在本机。iOS 退出或挂起 App 后不保证继续运行。

录音授权另行默认关闭。允许后，自动同步会上传本机已保存的录音，并下载本机缺少的云端录音；不会开启新的录音，也不会覆盖不同版本。关闭录音同步后停止后续上传与下载，已保存文件保留。双方都改过的文字或同一消息段不同的录音需明确处理，不自动选一边覆盖。本机删除不会顺带删除云端副本；已有本机检查点的删除记录也不会自动恢复。关闭自动同步不删除云端副本，仍可使用「立即同步」和单独的手动录音备份。

若出现 401，检查地址和手机令牌；若提示权限不足，确认 token 绑定的 Auth 用户存在且没有限制到单个联系人。不要通过关闭权限规则解决错误。Tincall 只接受明确配置的手机令牌、联系人令牌及经授权签发的 OAuth／唤醒凭据，不接受项目内普通 Supabase Auth 登录令牌。新版迁移收回普通登录用户对 Tincall 表、通话 RPC 和私有媒体的直连权限；文件通过已鉴权的连接端访问。专用于 Tincall 的项目也可在 Supabase 的 Authentication 设置中关闭公开注册；不要为此修改同项目其他应用需要的注册设置。

在 App 撤回连接的数据发送授权后，普通业务请求会被阻止；仍可向最后同意的原服务发送设备解绑请求，以停用后台来电。更改地址后，不能借解绑向新地址发送凭据。更新已部署服务时，需应用新增数据库迁移并更新函数；单独更新 App 不会修改远端服务，MCP 平台也需刷新工具定义。

## 4. 外部平台（可选）

仅备份无需这一节。MCP 在对应联系人的编辑页配置：通话方式选择 MCP，选已保存的服务并保存。传输方式推荐 HTTP（Streamable HTTP），平台仅支持 SSE 时再选 SSE；分别复制对应的 URL 和 Authorization，填入 AI 平台的服务地址和同名请求头。HTTP 地址为服务基础地址加 `/mcp`，SSE 为 `/mcp/sse`；旧部署须更新数据库迁移和服务函数才能使用 SSE。SSE 客户端需支持断线重连及 Last-Event-ID，HTTP 无需维护这条长连接。手机访问令牌在已保存的服务内只读查看／复制，新建连接时才填写。普通 MCP 需先在外部平台启动 AI，并通过工具等待输入。MCP＋唤醒桥通过事件启动每轮任务，接入见本页说明。只有后端转发接法才需要在 `TINCALL_BINDINGS` 配置真实的生成和取消 HTTPS 接口，不要将它与 MCP 唤醒订阅混用。

服务升级后，在外部 AI 客户端刷新工具列表或断开后重新连接。应看到 `tincall_call`、`tincall_get_call`、`tincall_wait`、`tincall_reply`、`tincall_end`、`tincall_list_calls` 六个工具。普通 MCP 的 `tincall_reply` 要求本通电话的 8 字符 `call` 标记和完整 `text`，可选 `wait_for_input`；唤醒桥由请求头绑定通话，只要求 `text`；不传 `reply_to`、轮次或分片。服务目前不主动推送工具列表变更通知，新开聊天也不保证重新获取定义。

HTTP 生成任务需要 worker 推进：在项目 Vault 设置 `tincall_function_base`（上述函数地址）和 `tincall_worker_token`（与服务端 worker token 一致），让迁移安装的 Cron 每分钟运行。接口、权限及限制详见 [连接端说明](../connector/README.md)。

## 5. 定时和后台来电（可选）

App 入口为「设置 → Tincall 云端 → 后台与定时来电」，先开启「允许后台来电」完成设备绑定，再在「定时来电」设置联系人与时间。备份和来电可共用 Supabase 项目与已保存连接；商店版构建 11 起，App 内部署或更新会在没有发送端时自动接入官方服务，但仍需手动开启后台来电并完成设备绑定。自签版与命令行部署仍需自己的发送端。不开启「允许后台来电」也能在 App 前台接听已配置联系人的来电，前提是服务连接与来电订阅正常。后台或锁屏接听还需要：

- 定时来电需要上述 Vault 和 Cron 配置。
- 自签版或命令行部署需部署一个与自己签名匹配的发送端：可选择支持 Node 24 与出站 HTTP/2 的服务器运行 `connector/apns-server.mjs`，或使用 Cloudflare Worker；两者不用同时部署。商店版构建 11 起使用上面的官方服务，不要为商店包配置个人签名的发送端。
- 服务端配置 Apple APNs 私钥、Team ID、Key ID、与 App 匹配的 VoIP topic；数据服务配置对应发送地址与服务间令牌。私钥不能进入手机或源码库。
- iPhone 安装具备 PushKit/APNs 权限的签名版本，在「后台与定时来电」完成真实设备绑定，再添加每日或每周计划。

计划行右侧开关用于暂停／启用；点计划内容打开编辑页，删除按钮位于编辑页底部。重复可选每天或每周一至周日，按所选时区执行；编辑已暂停计划不会自动启用，重新启用从下一次未来时间开始，不补打错过的来电。

计划设置需要当前服务及数据库迁移，按「更新已有服务」保留原配置升级即可。旧服务不支持时，App 会在写入新重复设置前提示更新，避免每周计划被当成每日保存。

自行构建或重签 IPA 的使用者，从 [自签推送配置](../cloudflare/README.md#自签后台来电配置步骤) 开始：其中说明 Apple 权限、最终 Bundle ID／App Group／topic 对应关系、两种发送端的配置命令、连接端 secrets 与手机绑定。作者的官方发送端不会自动支持其他签名团队或 App 标识，免费个人签名也不能通过部署云端补上推送权限。

发送进程及私密配置的完整字段见 [APNs 与计划说明](../connector/README.md#apns-sender-devices-and-schedules)。模拟器可检查 UI，不能替代真机锁屏响铃与接听验证。Cron 按分钟调度，不是精确到秒的闹钟。


## 排错与验证

| 现象 | 处理方式 |
| --- | --- |
| 服务提示缺少能力、旧参数或迁移 | 按原部署方式更新服务及全部迁移，再检查连接；只更新 App 不会更新远端 |
| MCP 仍出现 `reply_to` 等旧参数 | 刷新平台工具列表或断开重连；检查普通 `tincall_reply` 是否要求 `call`、`text`，可选 `wait_for_input`；唤醒桥只要求 `text` |
| MCP `Request timed out: tools/call` | 按下方 Kelivo／Muse 说明调整；其他平台按自己的工具请求时限设置。超时后继续 `tincall_wait`，不要直接重发正文 |
| 备份连接成功但没有同步 | 开启自动同步或点「立即同步」；录音保存及录音同步需分别允许 |
| 计划存在但手机不响铃 | 检查 Cron／worker、推送发送端、签名权限和设备绑定，按[推送排错](../cloudflare/README.md#常见配置问题)逐项核对 |

普通 MCP 的等待时长在联系人页设置：默认 120 秒，可填 1–130 秒，越界输入会自动调整。等待超时不挂断，朗读与等下一句都占用请求时间。Supabase 接法在等待结束前不返回响应，需避开其[请求空闲时限](https://supabase.com/docs/guides/functions/limits)。

Kelivo 的 MCP 请求超时默认 30 秒，请在其 MCP 设置中调至 180 秒并重新连接；通话过程中，Kelivo 需要保持在前台。

Muse 默认等待工具结果 45 秒，单次调用达到 120 秒会转入后台。将 Tincall 对应联系人的 MCP 等待时长设为 90 秒，并让 Muse 中的 TA 将工具等待时间设为 110 秒。这样 Tincall 会先结束本次等待；即使没有正常返回，Muse 也能在 110 秒时报告超时，让 TA 继续处理。若这一轮工具调用已结束，可以主动发消息唤醒 TA，继续通话。

AI 调用 `tincall_end` 后，手机等已收到回复实际播放排空再结束；手动挂断立即生效。普通打断停止当前生成和播放，但保持通话；已收到 AI 挂断请求时，打断剩余播放会完成挂断。播放失败也退出收尾。`tincall_wait` 等待新增消息、接听、挂断或正常超时，不因为播放停止就要求重发回复。

部署后依次验证：检查连接、一次真实同步或所选通话接法、已有服务升级后的数据保留。使用后台来电时，另外测试前台、后台、锁屏响铃及接听后的双向音频、挂断与实时活动。部署命令完成、APNs 接受请求、手机已绑定均不能代替这些行为检查。只使用独立模式的使用者无需部署或验证云端。

英文操作步骤见 [English setup guide](setup.en.md)。
